# Taste — Workflow

- Prefers UI-first development with mock data over domain/service-first: define service-layer contracts and in-memory mocks (seeded with demo data that mirrors the design prototype) up front, build all screens on that contract, then swap in real services incrementally behind the same interface so the app stays demoable from early on. Confidence: 0.8
- Likes structured decision gates before large steps (e.g., before publishing tickets, or when asked "berikutnya apa?"): the agent presents options with a recommended choice and the user typically approves the recommended path (e.g., picked the recommended T18 accessibility pass over the alternative work when offered the choice). But a prior approval is not final — the user may reverse a locked decision (e.g., switched from domain-first to UI-first with mock data), so re-plan flexibly without pushback. Confidence: 0.95

- After the user has approved a plan, expects the agent to execute immediately on a terse go-ahead (e.g., "aku sudah setuju tolong publish", "setuju semua", "Lanjutkan" right after a phase-completion summary with a recommended next step) rather than pausing for further confirmation rounds — approval of a decision frontier launches the whole multi-step execution, and this repeats at every phase boundary. Confidence: 0.8
- Wants work breakdowns (tickets) audited for completeness, detail, and granularity before publishing: every user story and prototype screen should map to a ticket, each ticket should be detailed (what to build + acceptance criteria + blocked-by references), and sized so one ticket = one screen or one domain service that fits a fresh context window — not too big, not too small. Confidence: 0.75
- Values design fidelity verified per screen: extract design tokens (colors, typography, radius, spacing) from the design prototype into tracked docs + TypeScript token files, and check each UI screen against the prototype via visual checklists (screenshot comparison, token/spacing/state checks) before considering it complete. Confidence: 0.7
- Handles OS/host-level maintenance (e.g., disk cleanup) themselves; once the user reports it done with a terse "lanjut", the agent should drop environment work and resume the project task rather than continuing to investigate or clean. Confidence: 0.6
- On terse continuation prompts — "lanjut"/"continue" to resume a session, or "berikutnya apa?" after a phase completes — expects the agent to reconstruct the pending context itself (disk state, plans/task ledger, git/repo state) and present a concise state summary with a recommended next step and its decision frontier, rather than asking the user to re-explain where things left off or to pick the sequencing unaided. Same after an accidental interrupt ("Aku tidak sengaja interrupt. Lanjutkan"): resume the exact pending step (e.g., re-issue the grilling round that was in flight) using facts already gathered instead of re-running the interrupted exploration or waiting on its sub-agent — exact per-detail facts get re-checked at execution time. Confidence: 0.7
- Expects the agent to own all investigation grunt-work itself — dispatching its own (parallel) explore sub-agents with structured, evidence-with-file-paths prompts to map the codebase — and only bring the user decisions paired with recommendations; the user's role is picking among recommended options ("aku mengikuti rekomendasi mu"), not doing research. Confidence: 0.6
- Once a real data path exists behind the same interface, prefers deleting the mock/test-double world outright (mock data files, mock service functions, module-level mock state) over relocating it to fixtures or keeping it as a demo mode — complements the UI-first mock workflow: mocks are development scaffolding, then get removed when the swap is complete. Confidence: 0.7
- Wants ALL dead/unused code removed during refactors, not just what's in direct scope: unused components, unused hooks, dead style blocks, and dead exports get deleted ("hapus saja semua code yang tidak digunakan lagi") as a dedicated step/commit rather than being left in the codebase "just in case". Verify an export is truly unused (grep for call sites) before deleting. When the only remaining user is the export's own test, don't keep test-only code in production: re-point the test at the surviving API via a local thin helper in the test file that reproduces the removed function's exact semantics (e.g., reverse the ranged query's ASC result to match the old DESC full scan) rather than loosening or rewriting the assertions. Confidence: 0.85
- Prefers refactors carved into small incremental steps — each step passing the project's verify gate and committed separately so every commit stays green and is revertable per screen/area; a component's tests are adapted in the same step as that component's refactor so no step is left red. Confidence: 0.7
- Prefers pure screens/components with mandatory explicit props — no default props that call services and no hidden fallback branches; deliberate no-op callbacks are passed explicitly at the call site so intent is visible rather than buried in defaults. Confidence: 0.7
- Keeps each refactor scoped to a single concern: adjacent fixes discovered mid-refactor get deferred to their own planned phase instead of being bundled (verifiability over completeness), while cheap fixes that make the new contract honest (e.g., renaming now-misleading types) happen in the current step and structural relocations wait for the phase that owns them. Confidence: 0.7
- The machine's shell is cmd.exe (Windows): bash-only syntax like `;`-separated compound commands fails — run diagnostics as separate simple commands, or use cmd-compatible syntax (`&` chaining, `2>nul`). Confidence: 0.9
- When a verify gate is red at baseline (e.g., 95 files failing `format:check` from historical drift, unrelated to current changes), do not block the functional step on it: gate functional commits on lint+typecheck+tests and schedule the fix as its own dedicated `style:` commit (e.g., `style: prettier`) rather than mixing formatting into functional refactors. Confidence: 0.6
- When reference docs/skills conflict with the actual codebase (e.g., a skill describing `(tabs)/` routing while the repo's file structure is factually flat), the codebase's reality wins over the documentation. Confidence: 0.7
- After a formatter run (`prettier --write`) mutates files mid-session, re-read the affected sections before applying edits — the exact text captured by earlier reads is stale ("Prettier mengubah file setelah read — baca ulang bagian yang akan diedit"). Confidence: 0.7
- Commit messages follow conventional commits with a scope (`refactor(report):`, `docs(adr):`), a bullet body enumerating each change of the step, and a `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer; messages are written to a scratchpad file and applied via `git commit -F`. Confidence: 0.8
- When rewriting screen tests with inline fixtures, first read the production types/service return shapes to build faithful fixtures; when a fixture-driven test fails, align the fixture with the component's actual behavior (real a11y labels, real naming rules) rather than loosening the assertion or changing production. Confidence: 0.7
- Durable architectural decisions are recorded as ADRs under docs/adr/ via the repo's domain-modeling skill (activate skill, read ADR-FORMAT.md, write in Bahasa Indonesia), committed separately as a `docs(adr):` commit. Confidence: 0.6
- Duplicated business logic gets extracted into small pure domain modules (`src/lib/domain/`, one file per concern — e.g., `ledger.ts` for money math, `period.ts` for period math, each kept under a ~400-line file budget): pure functions with no DB access and their own unit tests; services call these instead of re-implementing the same reduces/formulas inline, and near-duplicate helpers/dead modules found during the extraction are deleted in the same pass. Confidence: 0.8
- Overlapping utility modules get consolidated into one canonical module with one convention (e.g., merging `lib/calendar` into `lib/date` so there is a single date library): migrate helpers with identical behavior, treat the existing green tests as the safety net (a red test is a bug signal, not new behavior), and fold in latent edge-case fixes discovered during migration (e.g., UTC-anchored day arithmetic instead of `toISOString` on local-noon dates). Confidence: 0.75
- Components never import services: when a component needs a shared helper (e.g., `periodBounds`), it lives in a `lib/` module rather than being re-exported from the service — component→service import leaks get closed when found. Confidence: 0.7
- Each tab/feature gets a single read model under `features/<tab>/read.ts` exposing one `read<View>(database, …)` function (a barrel `index.ts` re-exports it; routes consume it via `useFocusedRead`): queries push down into SQLite — scoped fetches (calendar month for Daily, SQL `LIMIT` for recent transactions, period range for Report, `SUM … GROUP BY` aggregations) replacing full-table scans plus JS aggregation — and pass-through service modules get absorbed and deleted. Read/view types are narrowed to exactly what the screen uses (unused parameters dropped even when callers had them, unused snapshot fields removed with fixtures trimmed), re-implemented computations must reproduce the original semantics with the green tests as the safety net (e.g., spare budget counts stored expense items *plus* unplanned realized categories, not just stored rows), and each read model gets an integration test against a real in-memory SQLite with migrations + seed. The cache adapter (useFocusedRead) is kept as-is; swapping the caching layer belongs to a later phase. Confidence: 0.75
- Unrelated leftover changes discovered uncommitted mid-step (e.g., an earlier step's edits that never got staged, found via `git status`) are committed separately first — a leftover commit, then the current step's commit — instead of being mixed into the step's commit. Confidence: 0.7
- Tests must not assert transient intermediate states (e.g., a loading spinner between async operations): they are racy/flaky (the state can pass before waitFor catches it) — remove such assertions and let the final-outcome assertion decide. Confidence: 0.7
- In this repo's component tests, @testing-library/react-native v14's `render()` is PromiseLike — always `await render(...)` and make render helpers async. Confidence: 0.6
- When a gate reports errors that contradict the actual file contents, suspect stale tool caches (tsbuildinfo, node_modules/.cache / eslint resolution cache): verify the file with grep/read, run the tool directly on the affected files for a fresh verdict, and clear the cache when confirmed. Confidence: 0.6
- Oversized screens get split into a feature-local structure instead of staying monoliths or dumping everything into `components/`: section files live in `features/<tab>/screens/*.tsx` (summary card, section wrapper, item rows, form/payment modals), extracted state machines live in `features/<tab>/hooks/use-*.ts`, the parent screen file becomes pure composition (~1.700 → ~350 lines), and only genuinely cross-tab UI is promoted to `components/`. Duplicated screen-level logic (e.g., the AI suggestion state machine + AI bottom sheet duplicated across plan and report) is extracted once into a shared hook (`use-plan-ai`) + shared component (`ai-sheet-modal.tsx`) that both tabs consume, so fixes land in one place. Confidence: 0.75
- Theme and locale access is hook-only: components call `useTheme()` / `useLocale()` themselves — no prop-drilling of the `theme` object through internal components — and style blocks shared by several sections get their own module (e.g., `plan-sheet-styles.ts`). Confidence: 0.75
- Lint budgets with teeth are installed only after the codebase complies, so every commit stays green: `max-lines` as error at 600 (skip blank/comments) and `max-lines-per-function` as error at 300, with justified per-file overrides (e.g., `src/i18n.ts` until its own split) — prefer the honest, currently satisfiable bound over a stricter number that forces rushed slicing. Confidence: 0.75
- Prefer real types over casts: local `as never` / `Record<string, unknown>` type-hacks get replaced mid-refactor with the actual read-model types imported from the feature's `read.ts`, and leftover `as never` router casts get deleted as plain cruft once typecheck confirms they were unnecessary — `experiments.typedRoutes` turned out not to be needed and was left unenabled. Confidence: 0.7
- Extraction must preserve behavior parity — diff the new module against the original and restore anything lost in the move: the archive confirmation and save-error dialog that initially dropped out of the picker, the Donut's accessibility label (restored via the `useTranslation` hook, not a direct `i18n.t` call), and mode-dynamic labels (edit vs create) on header buttons.
